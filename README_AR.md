# محوّل قاعدة بيانات الأدوية المصرية إلى 96 حقلًا — الإصدار V2

هذا المشروع يقرأ قاعدة بيانات الأدوية المصرية العامة:
https://github.com/mahmoudfalous/eg-drugs/blob/main/data/eg_drugs.json

ويحوّلها إلى **96 حقلًا** وفق مخطط `schema_96.json`، مع الحفاظ على السجلات الأصلية في ملف منفصل، وإنتاج تقارير مراجعة.

**تحذير مهم:** المخرجات مسودات تقنية وليست بيانات طبية معتمدة. جميع السجلات الناتجة `is_active=0`. لا يجوز الاعتماد على قيم الصفر في حقول الوصفة أو المخاطر أو التفاعلات الدوائية لإثبات عدم وجود خطر. أي بيانات طبية يجب أن يراجعها صيدلي مؤهل قبل استخدامها.

## الباحث المتقدم سريع الاستجابة — البحث في الأدوية والنشرات

تم توسيع البحث الحالي دون تعديل محتويات أي دواء في ملفات JSON أو إعادة توزيع السجلات:

1. **`fast_drug_search.py`**: فهرسة **SQLite FTS5** للـ96/98 حقلًا المحوّل، باستخدام **BM25** بوزن أعلى للأسماء التجارية والعلمية، وتطبيع العربية (الهمزات، التشكيل، الأرقام العربية) والإنجليزية، والبحث التقريبي **Trigram** للأخطاء الإملائية، مع فهرس B-tree مباشر للـGTIN ورقم السجل.
2. **`fast_search.py`**: محرك بديل بذاكرة التشغيل يعتمد الفهارس المعكوسة ونقاط التشابه؛ مناسب لتشغيل بحث واحد دون الاحتفاظ بقاعدة SQLite على القرص.
3. **`research_batch.py`**: استرجاع النشرات من **openFDA** والرموز من **RxNorm** والمراجع من **DailyMed** باستخدام طلبات متوازية محدودة وذاكرة تخزين مؤقت، مع حذف استعلامات المواد الفعالة المكررة. يُعاد فحص كل منتج منفردًا مهما تشابهت مادته الفعالة مع غيره.
4. **`label_api.py`**: فحص حقلي `openfda.generic_name` و`openfda.substance_name` مع حد أقصى 100 سجل لكل حقل، وإزالة تكرار النشرات حسب `set_id` واختيار الإصدار الأحدث من النشرة نفسها، ثم التحقق الصارم من الاسم والتركيز وطريق الإعطاء. هذا **ليس بحثًا شاملًا لكل النشرات**، ولا يثبت أن المستحضر الأمريكي مكافئ للمستحضر المصري.

### استخدام محرك SQLite محليًا

```bash
python convert.py --download --sample 0 --include-catalog-details --output-dir full_catalog

python fast_drug_search.py --build-from full_catalog/drugs_96_DRAFT.json --index search.sqlite3

python fast_drug_search.py --index search.sqlite3 --query "كونكور" --limit 10

python fast_drug_search.py --index search.sqlite3 --query "Concor 10mg" --limit 10

python fast_drug_search.py --index search.sqlite3 --query "6221000003295" --limit 10
```

يعمل البحث في SQLite محليًا دون إنترنت بعد بناء الفهرس. الخيار `--full-record` يعرض بيانات JSON المحوّلة كاملة لكل نتيجة؛ دون تغيير السجل أو حقوله. إن ظهر باركود مشترك لأكثر من دواء، يُعلّم البرنامج النتيجة على أنها **تحتاج تحققًا** ولا يعلن فرادتها.

### سلامة بيانات الدواء وحدود البحث

- **الباركود الصحيح شكليًا لا يثبت تسجيل الدواء**. وكذلك تطابق الاسم العلمي لا يثبت تكافؤ العلامة التجارية أو التركيز أو الشكل الصيدلاني.
- يمنع محرك الفهرسة السجلات المتكررة في `id` أو `uuid`، ويعرض النتائج على أنها **اقتراحات بحث فقط**؛ ولا يملأ جرعات أو آثارًا أو تفاعلات غير مراجعة تلقائيًا.
- يستخدم الاستعلامات المعلّمة لحماية بحث SQLite من حقن SQL، ويسجّل تعارض التركيز عندما يطلب المستخدم تركيزًا يختلف عن تركيز المنتج.
- تتطلب واجهات openFDA الالتزام بحدود المعدّل والاستخدام؛ لإجراء بحوث متكررة يمكنك إضافة `OPENFDA_API_KEY` إلى GitHub Secrets بنفسك. تحتفظ الاستعلامات الخارجية بذاكرة مؤقتة بمدة صلاحية محددة، ولا تُرسل قاعدة بيانات الصيدلية كاملة إلى واجهات النشرات.
- مهمة **Export JSON batches** المنفصلة تبقى كما هي: **300 سجل أو أقل لكل ملف JSON محوّل** دون إدراج قاعدة المصدر الأصلية أو ملفات جانبية داخل ملفات الأدوية المضغوطة.

## برنامج مقارنة مخرجات التحويل والبحث — جديد

أُضيف برنامج **`compare_research.py`** وربطناه مباشرة بمهمة **Fast multilingual drug research** في GitHub Actions؛ يأخذ مدخلين منفصلين:

- **التحويل**: `catalog_temp/drugs_96_DRAFT.json`، وهو ملف الـ96 أو 98 حقلًا المحوّل (ليس قاعدة المصدر قبل التحويل).
- **الباحث**: `research_output/medical_sources_REVIEW_ONLY.json`، وهو سجل المراجع التي جُمعت من openFDA وRxNorm وDailyMed بعد البحث المحلي.

يفحص البرنامج رقم الدواء و`uuid` والاسمين العربي والإنجليزي والمادة الفعالة والتركيز والشكل الصيدلاني وطريق الإعطاء واسم الشركة عند وجوده. عند وجود اختلاف **يرفض مقارنة المعلومات لهذا المنتج**، ويعرض الاختلاف في التقرير دون إضافة حقل واحد. كما يمنع تكرار المعرّفات ويكشف اختلاف النصوص الطبية الموجودة عن نصوص النشرات المسترجعة.

**المخرجات:** `research_output/comparison_REVIEW_ONLY.json` يحتوي قائمة مستقلة لكل دواء وحالات **متطابق**، **ناقص ولديه مرجع**، **متعارض ويحتاج مراجعة**، **لا توجد له معلومات خارجية**. ويتضمن أيضًا `external_label_checks` الذي يميز تطابق سجل البحث مع قاعدة التحويل عن تطابق نشرة المنتج المحلي.

ينشئ `research_output/product_review_NOT_APPROVED.json` نماذج مراجعة مرتبطة بنفس `id` و`uuid` وبحقول طبية **فارغة**، مع `approved=false`. يقوم المراجع الصيدلاني بفحص نشرة **المنتج نفسه** وتوثيق المصدر واستكمال النصوص؛ بعد ذلك فقط يمكن استخدام `apply_reviewed_medical.py` لإنشاء نسخة جديدة من البيانات. **لا تعتمد الأداة صحة المعلومات الطبية أو تنفذ دمجًا تلقائيًا**.

### تشغيل المقارنة محليًا

```bash
  --research research_output/medical_sources_REVIEW_ONLY.json \

```

## ملف مراجعات حقيقي — خمسة مستحضرات ميتفورمين (غير معتمد طبيًا بعد)

أُنشئ ملف `reviews/metformin_5_REVIEW_REQUIRED_NOT_APPROVED.json` من نتائج البحث الفعلية، وهو يتضمن أرقام `id` و`uuid` والأسماء التجارية والتركيزات والأشكال الصيدلانية الخاصة بخمسة مستحضرات حقيقية في قاعدة الأدوية المحوّلة (614 و2576 و2577 و2578 و2579).

**لم تُعتمد البيانات الطبية لهذه المنتجات.** عُثر على مرجع أمريكي للمادة الفعالة فقط؛ لا يوجد إثبات بأن النشرة الأمريكية نفسها معتمدة للعلامات التجارية المصرية المذكورة. لذلك يحتفظ الملف بكل `reviewed_fields` فارغًا، و`approved=false`، و`exact_local_product_label_verified=false`، و`source_url` فارغًا إلى حين تقديم نشرة المنتج المحلي المعتمدة ومراجعة صيدلي مؤهل. لا يجوز تغيير هذين العلمين بقصد تجاوز بوابة المراجعة دون مراجعة فعلية؛ فالبرنامج لا يتحقق من مؤهلات المراجع بنفسه.

لإكمال الملف: أدخِل نص كل حقل بعد التحقق من **المنتج المحلي ذاته**، واحذف الحقول الفارغة، واكتب اسم المراجع المؤهل وتاريخ المراجعة، وضع رابط النشرة الصحيحة في `source_url`. استخدمه في خيار `approved_medical_file` فقط بعد اكتمال هذه الخطوات، لا قبلها. عند وجود ملف غير معتمد يفشل التصدير المشروط بأمان، بينما يبقى التصدير العادي دون موافقات متاحًا.

## الربط النهائي: البحث + المقارنة + التحويل + الدمج الموثّق + تصدير 300 JSON

أُضيفت ثلاثة مكونات مترابطة:

- `compare_research.py` يقارن نتائج البحث مع سجلات `convert.py` ويفحص أسماء الأدوية والمواد الفعالة والتركيز والشكل والطريق و`id` و`uuid` والشركة، وينشئ نماذج مراجعة للبيانات المفقودة أو المختلفة. **لا يقبل البيانات الطبية تلقائيًا**.
- `verified_merge_export.py` لا يسمح بتحديث الحقول الطبية إلا بعد وجود بيانات تمت مراجعتها على مستوى المنتج **بالضبط**، وبشرط أن تكون الحقول قابلة للمراجعة في مقارنة البحث، ولا يوجد تعارض غير محسوم. يستدعي `apply_reviewed_medical.py` لفحص حقول الهوية والمراجع وأسماء المراجعين والتواريخ.
- `approved_research_pipeline.py` هو برنامج الربط: يأخذ أرقام الأدوية المعتمدة من ملف الموافقات، ويسترجع المصادر لها بوساطة `research_batch.py` **باستخدام الـID الأصلي مباشرةً** لتجنّب اختيار منتج مشابه بالاسم، ثم يمرر البيانات إلى المقارنة والدمج ويعيد تصدير القاعدة كاملةً في أجزاء JSON لا تتجاوز **300** سجل.

### طريقة التشغيل من GitHub Actions

1. نزّل نموذج <https://github.com/abdallah1mohmmed2/pharmacy-drugs.-/blob/main/examples/approved_exact_product_TEMPLATE.json> ولا تعتمد النموذج كما هو.
2. بعد مراجعة **النشرة الرسمية للمستحضر المحلي نفسه** لدى صيدلي مؤهل، استبدل معرّفات الدواء من ملف JSON المحوّل كما هي، واملأ الحقول التي ثبتت صحتها فقط، واحذف الحقول التي لم تُراجع. التوثيق الحالي هو إقرار بالمراجعة، **وليس تحققًا آليًا من مؤهلات المراجع أو تسجيل المنتج**.
3. في ملف الموافقات، ضع `approved: true` و`exact_local_product_label_verified: true` **فقط بعد إتمام التحقق الحقيقي**، مع `reviewed_by` و`review_date` و`source_url` الخاص بالنشرة المعتمدة للمستحضر. لا يجوز نسخ النصوص الأمريكية لمجرد تشابه المادة الفعالة.
4. أضف ملف المراجعات إلى مكان في المستودع مثل `reviews/approved_products.json` (حتى **30** سجل مراجعة في تشغيل واحد حاليًا). **تنبيه خصوصية:** مستودع GitHub هذا قد يكون عامًا، فلا ترفع بيانات شخصية غير مخصصة للنشر؛ يمكن تشغيل السكربت محليًا بملف الموافقات بدل رفعه إلى مستودع عام.
5. افتح [Export JSON batches](https://github.com/abdallah1mohmmed2/pharmacy-drugs.-/actions/workflows/export_json_batches.yml)، واضغط `Run workflow`، وأدخل `approved_medical_file = reviews/approved_products.json`. اتركه فارغًا إذا أردت التحويل العادي **بلا أي دمج طبي**.
6. بعد النجاح، نزّل ملفات `drugs-96-json-batch-XX` من Artifacts. كل ملف مضغوط يحتوي **JSON محوّلًا فقط**، بحد أقصى 300 دواء، ولا يحتوي ملفات المصدر أو تقارير المقارنة أو النشرات الجانبية.

**مهم:** التصدير يبدأ من المصدر الأصلي في كل تشغيل. لذلك إذا أعدت التشغيل بموافقات مختلفة، يجب تضمين جميع الموافقات التي تريد المحافظة عليها ضمن ملف المراجعة المُقدَّم في هذا التشغيل. الموافقات القديمة **لا تُرحّل تلقائيًا** إلى تشغيل جديد.

### الاستخدام من Python دون رفع الموافقات إلى مستودع عام

```bash

  --catalog full_catalog/drugs_96_DRAFT.json \
  --approvals reviews/approved_products.json \
  --output-dir verified_export \

```

بعد نجاح التشغيل، **للتصدير فقط** استخدم `verified_export/json_batches/batch_01.json` إلى `batch_NN.json`. توجد نسخة من ملف البيانات الكامل وتقرير تدقيق للمراجعة **خارج مجلد `json_batches`**، ولا يتم رفعهما ضمن ملفات Artifacts.

وإذا كان لديك تقرير بحث محفوظ من تشغيل سابق، يمكنك إعادة تطبيق المراجعات مع المقارنة دون إرسال طلبات جديدة إلى API باستخدام:

```bash
python verified_merge_export.py \
  --catalog full_catalog/drugs_96_DRAFT.json \
  --research medical_sources_REVIEW_ONLY.json \
  --approvals reviews/approved_products.json \
  --output-dir verified_export
```

**حدود الاعتماد:** كل السجلات الناتجة تبقى `is_active=0` حتى يوافق نظام الصيدلية المسؤول على استخدامها؛ تعني `approved=true` إقرارًا من مُعدّ ملف المراجعة ولا تستطيع هذه البرامج التحقق وحدها من مؤهلاته، أو من أن الرابط يمثل نشرة المنتج المحلي الصحيحة. عند غياب موافقات صالحة أو وجود تناقض في الهوية أو الحقول، يتوقف مسار الدمج دون إخراج دفعات معتمدة مزعومة. لا يُعد تطابق البحث في النشرات الأمريكية اعتمادًا طبيًا.

## تطوير الحقول: اسم الشركة والتصنيف والتعبئة

أُضيف **الوضع الموسّع** إلى مهمة Export JSON batches. تُبقي كل سجلات JSON الحقول **96 الأصلية دون تغيير في أسمائها**، وتضيف حقلين للعرض فقط، لأن المخطط الأصلي لا يحتوي خانة نصية لاسم الشركة أو وصف العبوة:

- `manufacturer_name`: اسم الشركة كما ورد في المصدر الأصلي `company`، دون اختلاق `manufacturer_id` رقمي.
- `package_description`: وصف العبوة عندما يمكن قراءته بوضوح من اسم المنتج؛ مثل `30 tablets`.
- `units_per_pack`: عدد الوحدات حين يكون واضحًا من اسم المنتج، وليس من القيمة المبهمة `units` بالمصدر.
- `pharmacologic_class`: يُستخرج فقط من تصنيف مصدر مكتوب بصيغة من مستويين `therapeutic.pharmacologic`. هذا ليس رمز ATC معتمدًا.
- `dosage_form`, `route`, `strength_text`: من اسم المنتج إن توفرت قرائن واضحة. `route` تعني **مسار إعطاء الدواء** وليس **تعليمات استخدامه للمريض**.

كل ملف صادر من هذا الوضع الموسّع يحتوي **98 مفتاحًا** (96 أساسيًا + 2 معلومات عرض إضافية). **إذا كان نظام استيراد الصيدلية لا يقبل سوى 96 حقلًا، فيجب إضافة الحقلين الجديدين إلى مخطط الاستيراد أو تشغيل `convert.py` بدون `--include-catalog-details` للالتزام الصارم بـ96 مفتاحًا.**

### الجرعة العلاجية وطريقة الاستخدام وموانع الاستعمال

لا يحتوي مصدر eg-drugs الأصلي على هذه التفاصيل الموثوقة لكل منتج. لذلك **لا** يحوّل البرنامج التركيز `strength_text` إلى `dosage_administration`، ولا يفترض أن النشرات الأمريكية العامة تطابق كل المستحضرات المصرية. `clinical_candidates.py` يوفر نصوص النشرات المرجعية مع معلومات المطابقة، لكن حقول الجرعات وموانع الاستعمال لا تُملأ إلا بعد مراجعة وتوثيق هوية المنتج والتركيز والشكل والنشرة المختصة. تبقى كل السجلات `is_active=0` افتراضيًا.

## التفاعلات الدوائية والآثار الجانبية — استرجاع مُوثّق للمراجعة

تستخدم `safety_sections.py` و`label_api.py` و`clinical_candidates.py` النشرات الرسمية الأمريكية عند وجود **مادة فعالة مطابقة**، وتحفظ نصوص الأقسام كما وردت في النشرة مع حقل المصدر والرابط:

- `drug_interactions` ← مسودة لمراجعة `interactions_summary` مع سرد النص الأصلي للتفاعلات. لا يجري استنتاج درجة خطورة التفاعل من عنوان القسم.
- `adverse_reactions` و`adverse_reactions_table` ← مصدر للآثار الجانبية، دون نسخه كاملًا إلى `side_effects_common` أو `side_effects_serious`؛ فالقسم قد يجمع النوعين.
- `warnings_and_cautions` و`boxed_warning` ← معلومات عن مخاطر مهمة، **وليست دائمًا قائمة آثار جانبية خطيرة**.

توضح `safety_review.sections` النص الأصلي و`source_field`، وتعرض `safety_review.review_targets` مؤشرات لفظية مثل `most common adverse reactions` و`serious adverse reactions`. وجود المؤشر لا يصنف أي حدث طبي تلقائيًا. كل هذا **للمراجعة وليس معلومات سريرية معتمدة**.

عند تشغيل مسار **Probe interactions and adverse reactions (REVIEW ONLY)** من GitHub Actions، يُنتج ملف `medical_safety_review_TEMPLATE.json` يحتوي على هوية الدواء والحقول الثلاثة التالية **فارغة** مع `approved=false`:

```json
{
  "approved": false,
  "reviewed_fields": {
    "interactions_summary": "",
    "side_effects_common": "",
    "side_effects_serious": ""
  }
}
```

هذه صورة مبسطة للحقول؛ يتضمن الملف الحقيقي `id` و`uuid` واسم الدواء وتركيزه وشكله ومصدر النشرة. على الصيدلي المؤهل التحقق من **نشرة المنتج المصري نفسه**، وملء النصوص الصحيحة وحذف الحقول الفارغة وتوثيق تاريخ المراجعة واسم المراجع، ثم اعتماد سجل المراجعة يدويًا. بعدها يمكن استعمال `apply_reviewed_medical.py` لإدخال النصوص المدققة في نسخة JSON جديدة؛ يُمنع تغيير هوية الدواء أو ملء الحقول ببيانات تخص مادة فعالة عامة بلا تطابق منتج.

صفحة تشغيل الاختبار:
https://github.com/abdallah1mohmmed2/pharmacy-drugs.-/actions/workflows/probe_clinical_labels.yml

اختبار على 19 منتجًا من المصدر الحقيقي: وُجدت أقسام تفاعلات لـ14، وأقسام آثار جانبية لـ15، وتحذيرات لـ16، مع مؤشرات نصية على الشيوع في 10 وعلى الخطورة في 6. هذه أعداد توفر الأقسام في **عينة فقط**، وليست معلومات طبية معتمدة أو نسبة نجاح على كامل قاعدة البيانات. بقيت 16 مطابقة على مستوى المادة الفعالة فقط ولم تُثبت مطابقة المنتج التجاري المصري، واحتاجت 3 حالات تحققًا إضافيًا. جميع نماذج المراجعة الـ16 غير معتمدة افتراضيًا.

## محرك البحث المحسّن: الفهرسة والمطابقة متعددة المصادر

أُضيف `fast_search.py` للبحث في **قاعدة JSON المحوّلة** (98 حقلًا في الوضع الموسّع، أو 96 حقلًا في الوضع الأساسي)، باستخدام:

1. **تطبيع Unicode** والبحث بالعربية والإنجليزية؛ يشمل الهمزات والتشكيل والأرقام العربية والفارسية.
2. **فهرس عكسي Inverted Index** للكلمات، مع البدء بالكلمات الأقل شيوعًا وإجراء تقاطع مجموعات المرشحين لتقليل وقت البحث.
3. **فهرس ثلاثة أحرف Trigram** للبحث التقريبي عند اختلاف كتابة اسم الدواء.
4. **مطابقة حرفية للباركود والمعرّف**، مع ترتيب Field-aware يعطي الاسم التجاري والاسم العلمي أوزانًا مختلفة، وعقوبة لعدم تطابق التركيز.
5. **منع الدمج الصامت**: كل منتج يحتفظ بمعرّفه وUUID وأسمائه، ونتائج البحث ليست اعتمادًا لهوية المنتج طبيًا.

أُضيف `research_batch.py` لربط المرشحين بمصادر رسمية مستقلة من حيث الخدمة: [openFDA](https://open.fda.gov/apis/drug/label/)، و[RxNorm](https://lhncbc.nlm.nih.gov/RxNav/APIs/)، و[DailyMed](https://dailymed.nlm.nih.gov/dailymed/app-support-web-services.cfm). يستخدم طلبات متوازية **محدودة بثلاثة عمال كحد أقصى**، ويتجنب استعلام المادة العلمية نفسها أكثر من مرة داخل الدفعة، ويخزن نتائج الطلبات مؤقتًا لمدة 14 يومًا مع محاولات إعادة عند أخطاء الاتصال. **تعدد المصادر لا يعني تلقائيًا تعدد أدلة مستقلة على المنتج**؛ قد تستند openFDA وDailyMed إلى نشرة SPL واحدة.

## الاستكمال الطبي بعد مراجعة صيدلانية

يتضمن المشروع الآن `apply_reviewed_medical.py` لاستكمال الحقول الطبية مثل `dosage_administration` و`contraindications` و`warnings_precautions` **فقط عندما يوجد ملف مراجعة طبي موثّق لكل منتج**. يتم رفض الخلط إذا اختلف اسم المنتج أو `id` أو `uuid` أو المادة العلمية أو التركيز أو الشكل أو طريق الإعطاء، ويرفض البرنامج الكتابة فوق نص دوائي موجود أو إدخال علم مخاطر غير معتمد.

مثال لملف `approved_medical.json` (القيم الوصفية مكانها الحقيقي بعد المراجعة وليست توصية طبية):

```json
[
  {
    "id": 123,
    "uuid": "THE_EXACT_UUID_FROM_EXPORTED_DRUG",
    "trade_name_en": "EXACT_TRADE_NAME_FROM_JSON",
    "scientific_name": "EXACT_INGREDIENT_FROM_JSON",
    "strength_text": "EXACT_STRENGTH_FROM_JSON",
    "dosage_form": "EXACT_FORM_FROM_JSON",
    "route": "EXACT_ROUTE_FROM_JSON",
    "approved": true,
    "reviewed_by": "QUALIFIED_PHARMACIST_NAME",
    "review_date": "2026-11-10",
    "source_url": "https://example.org/exact-product-approved-leaflet",
    "reviewed_fields": {
      "dosage_administration": "PASTE_VERIFIED_PRODUCT_DIRECTIONS_HERE",
      "contraindications": "PASTE_VERIFIED_PRODUCT_CONTRAINDICATIONS_HERE"
    }
  }
]
```

```bash
python apply_reviewed_medical.py --input converted.json --approvals approved_medical.json --output reviewed_draft.json
```

**لا يُعد ذكر اسم مراجع في ملف JSON إثباتًا لهويته**؛ يجب التحقق خارجيًا من المراجعة والنشرة قبل الاستيراد الفعلي. هذه الأداة لا تعتمد المنتجات تلقائيًا، ولا تتدخل في مخرجات الـ300 دواء المعتادة. النشرة الأمريكية الخاصة بمادة فعالة لا تعني أنها النشرة المعتمدة لنفس المنتج المصري.

## إخراج JSON فقط — كل ملف لا يتجاوز 300 دواء

لتحميل **ملفات JSON فقط دون البيانات الأصلية أو CSV أو ملفات المراجعة**، افتح:

https://github.com/abdallah1mohmmed2/pharmacy-drugs.-/actions/workflows/export_json_batches.yml

- اختر `Export JSON batches - up to 300 drugs each`، ثم `Run workflow`.
- اختر `batch_size = 300`.
- سيُنشئ البرنامج قاعدة الـ96 حقلًا الأساسية مع اسم الشركة والتعبئة من نفس `convert.py`، ثم يقسم الناتج إلى أجزاء متتالية دون تكرار أو فرز أو تعديل أي سجل.
- لكل جزء Artifact مستقل باسم `drugs-96-json-batch-01`، `...-02`، إلخ. **داخل كل ملف ZIP يوجد JSON واحد فقط** باسم `batch_01.json`، إلخ.
- على إصدار المصدر الذي يحتوي **27,617** دواءً ومع حجم 300 سيكون هناك **93 ملفًا**: 92 ملفًا × 300 دواء، وملف أخير يحتوي على 17 دواء.
- يرفض البرنامج أي تكرار في `id` أو `uuid`، أو اختلاف في حقول المخطط الـ96، ويتحقق أن جمع الأجزاء يعيد نفس سجلات JSON الأصلية بنفس الترتيب. لا يحاول دمج سجلين يبدوان متشابهين ولكن بمعرّفين مختلفين؛ فهما قد يكونان مستحضرين مختلفين.
- **لا يرفع سير العمل هذا** `eg_drugs_original.json` أو `original_records.jsonl` أو `mapping_audit.csv` أو `manifest.json` إلى Artifacts. يتم استخدام هذه الملفات مؤقتًا للتحقق داخل GitHub Actions فقط.
- النسخ الناتجة **مسودة غير معتمدة طبيًا**، وجميعها تحتوي نفس الحقول الصيدلانية الـ96 دون إضافة بيانات سريرية لم تتم مراجعتها.

## ما الجديد في الإصدار 2.1؟

المشكلة السابقة أن الحقول المنقولة من ملف المصدر كانت محدودة. الآن يقرأ `product_name_parser.py` اسم المنتج باللغة الإنجليزية ويستخرج **عند وضوح الصيغة فقط**:

- `dosage_form` مثل TABLET وSYRUP وCREAM.
- `route` مثل ORAL وTOPICAL وOPHTHALMIC عندما يكون دليلها واضحًا.
- `strength_text` و`strength_value` و`strength_unit` مثل `10mg` أو `0.5%`.

لا يتم استنتاج جرعات الاستخدام للمرضى، ولا تُحوّل التركيبات متعددة المواد أو `10mg/2ml` أو `10/25mg` إلى تركيز عددي واحد. الحقول المستخرجة من الاسم **مبدئية** وتظهر أدلتها في `mapping_audit.csv` وفي ملخص `manifest.json`.

**جلب النشرات الطبية:** اختر `clinical_candidates=20` في GitHub Actions لتجربة الاسترجاع. يعيد `clinical_candidates.py` المعلومات بطريقتين فقط:

1. `CANDIDATE_REQUIRES_PHARMACIST_REVIEW`: المنتج الأمريكي المحتمل متطابق في المادة العلمية والاسم التجاري والتركيز وطريقة الإعطاء ضمن شروط البرنامج؛ تبقى المراجعة مطلوبة.
2. `INGREDIENT_REFERENCE_ONLY_NOT_PRODUCT_MATCH`: معلومات من نشرة أمريكية تخص المادة العلمية، ولكن **ليست دليلًا على أنها النشرة الصحيحة للمنتج المصري**. تظهر المعلومات في `reference_fields` ولا تُكتب في `drugs_96_DRAFT.json` بأي حال.

إذا لم يجد المصدر معلومات مؤكدة، لا يخترعها البرنامج. القيم الافتراضية مثل الصفر لا تعني أن الدواء آمن أو بلا تحذيرات. قد تظل أسعار السوق المحلية والشركة كمرجع رقمي وأرقام التسجيل والقيود الوطنية غير معروفة.

**اختبارات التكامل:** `.github/workflows/tests.yml` الآن يجري اختبارات دون إنترنت، وبعدها يفحص التحويل على أول 20 سجلًا من المصدر الحقيقي ويحفظ معاينة وتقارير في Artifacts.

## مبادئ حماية البيانات

- المصدر `active` هو اسم المواد الفعالة وليس حالة تنشيط السجل.
- أسعار المصدر بالجنيه المصري؛ لا تُعامل كأسعار صيدلية بالعملة المحلية.
- `units` لا يُفترض أنه عدد الأقراص.
- لا نعيّن تلقائيًا `requires_prescription` أو `is_controlled` أو جرعات الأطفال أو الحمل والرضاعة.
- يمنع البرنامج استبدال مجلد نتائج موجود ويستخدم بصمات للملفات.
- إن ظهر ملف `FAILED.txt` أو `preflight_errors.json` فلا تعتمد النتائج.
